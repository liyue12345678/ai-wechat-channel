# 🛠️ [实测] Dify深度体验30天：从不会写代码到做出3个自动化Agent，我的真实上手记录

> 📂 合集：**🛠️ 工具实测** | 模板：tool-review.md
> 发布日期：2026-07-30（周四）
> 适用对象：想用AI自动化工作但不会编程的人、在Dify和扣子之间纠结的人

---

**一个月前，我在Dify上搭了第一个Agent——一个"每天早上9点把天气预报发到飞书群"的小功能。那时候我连"API"三个字母代表什么都不知道。**

一个月后，我做了三个在生产环境里真正在跑的自动化Agent：一个帮我监测竞品动态，一个自动整理微信收藏进知识库，一个每天帮我筛选行业新闻并写摘要。

**这篇文章不是一个工具测评——是一份30天的真实日记。包括我三次想放弃的时刻、两个让我撞了三次墙的概念、以及最后为什么觉得"这一个月花得值"。**

如果你在犹豫要不要学Dify，或者已经在扣子和Dify之间纠结，看完这篇你应该能做出决定。

⏱ 阅读时间：约12分钟
💰 Dify开销：¥0（开源版自己部署）

## 先給你一个结论：Dify不适合所有人

在上周二的对比文章里，我给了Dify"上手难度⭐⭐⭐⭐"的评价。用了一个月后，这个评价不变——**甚至应该加半颗星。**

Dify不是扣子。它不会在你第一次打开的时候给你10个模板让你选。它的界面第一眼看上去像一个开发工具——因为它的确是。

**但这也是它最大的价值：它不是让你"用一个产品"，而是让你"组装自己的AI基础设施"。**

什么人适合Dify：
- 愿意花一个周末学习基本概念的人
- 需要私有化部署、数据不出公司的人
- 想做的自动化超过"问答Bot"复杂度的人

什么人不适合：
- 只想花20分钟搭个Bot发飞书群 → 去用扣子
- 完全不理解"API""JSON""变量"这些词也不想理解 → 去用扣子
- 只需要知识库问答 → 扣子或Coze都行

如果你属于第一类——继续往下看。我会把一个月踩过的坑全摊开。

## 第1-3天：搭建环境——第一个坑就来了

Dify的部署有两种方式：云端SaaS版（dify.ai直接注册）和开源版自己部署。

我选了开源版，用Docker部署在自己的服务器上。理由是数据完全在自己手里——我的工作文档、客户信息、竞品数据都不经过第三方。

**坑1：Docker部署没有想象中简单**

官方文档说"一条命令搞定"。实际过程是：

1. 装Docker Desktop（Windows上需要先启用WSL2，这一步就卡了我半小时）
2. clone Dify仓库 → `docker compose up -d`
3. 报错：端口冲突。我本地的Nginx占用了80端口
4. 改了端口 → 又报错：postgres容器启动失败，因为上次装别的工具残留了一个同名容器

**最后花了大约3个小时才把Dify跑起来。** 如果你是Mac用户会顺畅很多，Windows用户要有心理准备。

但部署完成后，成就感是真实的——浏览器打开 localhost:3000，看到Dify的登录界面，那一刻你觉得自己"拥有了"一个AI平台，而不是"租用了"一个。

**第一课：Dify的SaaS版和开源版的核心功能几乎一样。** 如果你不需要私有化部署，直接用SaaS版——把省下来的3小时花在真正重要的东西上。

## 第4-7天：第一个Agent——"竞品监测"撞了三次墙

上一篇对比文章里，我在三个平台（扣子、Dify、Coze）上搭了同一个"竞品监测Agent"作为测试。那是在Dify上搭的第4天。

### 撞墙1："知识库"不等于"搜索引擎"

我的第一版设计是：Agent每天自动搜索竞品信息 → 和知识库里的历史数据对比 → 发现变化就推送。

搭完之后发现一个致命问题：**Dify的知识库检索和联网搜索是两个独立的能力，要让它们"配合"需要写逻辑。**

具体来说：Agent搜到了竞品A降价的信息 → 它怎么知道"降价了"？它需要去知识库里查"竞品A之前的价格" → 但默认工作流不会自动做这一步。

**解决方案：在工作流里加了一个"条件判断"节点——如果搜索结果里检测到价格关键词，就触发知识库检索做对比。** 这个逻辑在扣子里也需要配，但扣子的模板帮你预置了类似的结构。Dify需要你自己从头搭。

### 撞墙2：Webhook调试让人崩溃

Agent要把简报推送到飞书群，需要配置飞书的Webhook。这个过程在Dify里是：

1. 在飞书群里添加自定义机器人 → 拿到Webhook URL
2. 在Dify工作流里加一个"HTTP请求"节点
3. 手动写JSON格式的消息体

**第3步我卡了整整一个下午。** 飞书的消息格式是一套嵌套的JSON结构。少一个逗号、多一个花括号，飞书就收不到消息。而Dify的HTTP节点报错信息是"请求失败"——不告诉你是URL错了、格式错了还是飞书那边拒了。

最后我在Dify社区里搜到一篇帖子，有人分享了飞书消息的JSON模板。复制过来改了10分钟就通了。

**第二课：Dify的调试体验对非技术用户不友好。** 扣子有"飞书消息"插件——选群、填内容、点发送。Dify让你手写JSON。这是Dify最大的学习成本来源。

### 撞墙3：定时触发不稳定

我把Agent设置成每天早上9点自动运行。前三天好好的，第四天没触发。

排查了半天发现：**Dify开源版的定时任务依赖Celery，而Celery的worker进程偶尔会挂掉。** 官方的解决方法是加一个健康检查脚本或者用外部的cron来触发API。

我最终用了最笨的办法：在服务器上设了一个crontab，每天早上8:59调Dify的API来触发工作流。绕过了内置的定时器。

**第三课：Dify开源版需要一定的运维意识。** 它给你的自由度是"你可以修任何东西"，但前提是"你知道怎么修"。

## 第8-14天：第二个Agent——我放弃了，然后又捡起来

搭完竞品监测Agent后，我膨胀了。决定做一个更复杂的："知识库自动收纳Agent"——把微信文件传输助手里攒的文章自动分类、摘要、存进知识库。

### 为什么放弃

这个Agent需要的能力比竞品监测多一个数量级：
- 读取多个来源（微信文件、网页链接、PDF）
- 对每篇文章自动提取：标题、核心观点、类型、和已有知识的关联
- 处理完成后更新一个索引文档

我在Dify的工作流画布上搭了17个节点——触发器、文件解析、文本分块、LLM提取、知识库检索、条件分支、循环迭代、HTTP写入……然后工作流一跑就超时。

**Dify免费版的工作流有30秒的执行限制。** 处理一篇长文章就需要20-30秒，批量处理3篇直接超时。

我当时觉得"这个平台限制太多了"，关掉Dify，一周没打开。

### 为什么又捡起来

一周后我在整理微信收藏（正好是写"第二大脑"教程那天），手动整理了3个小时。突然意识到：**我嫌Dify限制多，但手动做的痛苦比限制的痛苦大多了。**

重新打开Dify，换了一个思路：不追求"全自动"。把Agent拆成两步——第一步：我手动把文件拖进Dify知识库（30秒）；第二步：Agent在知识库更新后自动触发，对新文件做分类和摘要（10秒）。

**拆成两步后，每个工作流只需12秒。而且多了一个好处——我手动筛选了"什么东西值得进知识库"。** 这个Agent到现在每天都在跑，帮我处理每天新增的5-10篇文章。

**第四课——也是这个月最重要的教训：不要一上来就追求完美自动化。** 80%自动化+20%人工判断，往往比追求100%自动化更稳定、更实用。Dify的能力边界不在于"能做什么"，而在于"什么粒度最合适"。

## 第15-21天：第三个Agent——意外的惊喜

前两个Agent已经让我对Dify的工作流逻辑比较熟悉了。第三个Agent的搭建只用了2小时。

### Agent 3："AI新闻早餐"

每天早上8点，自动搜索过去24小时的AI行业新闻 → 按"重要度"和"跟我相关的程度"排序 → 每篇生成3句话摘要 → 推送到我的飞书。

这个Agent的技术含量其实不高——就是一个"定时搜索+LLM摘要+推送"的流水线。但因为我对Dify已经熟了，搭建过程非常流畅。

**真正让我惊喜的是：这个Agent跑了一周后，它开始"认识"我关注的话题了。** 因为我每次读完简报后，会在飞书群里给某些新闻发个表情——Agent的工作流里有一个"读取群消息反馈"的节点。它学会了：我发👍的新闻类型，第二天同类型的新闻会排在前面。

**这不是"机器学习"，就是简单的规则——但它让我第一次感受到"AI在适应我"的感觉。**

**第五课：好的Agent不需要很复杂。** 我的三个Agent里，技术复杂度最高的是知识库收纳（17个节点），但日常使用频率最高、我觉得最离不开的，是最简单的新闻简报（6个节点）。不要追求复杂度——追求"真的每天用"。

## 第22-30天：我开始理解了Dify的设计哲学

用了一个月后，我终于理解了Dify和扣子的本质区别。

### 扣子是一辆"智能汽车"

你坐进去，告诉它去哪，它自己规划路线、避开拥堵、找停车场。你不需要知道发动机怎么工作——但你也不能改装它。想去的地方如果导航上没有，你就去不了。

### Dify是一个"工具箱"

给你发动机、轮子、方向盘、座椅——你自己组装。你可以装成轿车、卡车、甚至飞机。但前提是：你得知道这些东西怎么拼在一起。

**Dify的产品逻辑是：我们提供所有零件，你决定怎么组装。扣子的产品逻辑是：我们提供10款成品车，你选一辆开走。**

这不是哪个好哪个不好的问题——是"你需要什么"的问题。

## 如果你要开始学Dify，我有一条"避坑路线"

回顾这30天，如果我一开始就知道下面这几件事，至少能省下一半时间：

### 第1步：先别部署，用SaaS版体验3天

去 dify.ai 注册一个账号。在云端搭一个最简单的Agent——哪怕只是"输入一句话→AI回复一句话"。先感受一下工作流画布的逻辑。

**不要一上来就折腾Docker。** 部署是整个Dify学习曲线里最陡的一段——把它留到你确认"我真的要用Dify"之后。

### 第2步：理解3个概念，后面的路好走10倍

Dify里最难的不是操作，是概念。这三个概念搞懂了，70%的障碍就没了：

1. **变量（Variable）**：工作流里的"便签纸"。上一个节点的输出存进变量，下一个节点从变量里读。所有数据传递都靠它。

2. **JSON**：一种数据格式。看起来像这样：
```json
{"title": "AI新闻", "content": "今天OpenAI发布了..."}
```
你不用学会写JSON——你只需要知道：**当你看到花括号和引号的时候，你在处理"结构化的数据"。** 大部分报错都是因为花括号没配对。

3. **API和Webhook**：API是你"主动去别人的服务器拿东西"；Webhook是"别人主动推给你东西"。你只需要知道这两者的区别——具体怎么配置，网上有无数模板可以复制。

### 第3步：先抄再改，别从零搭

Dify的社区里有大量别人分享的工作流模板。找到和你需求最接近的一个 → 导入 → 跑一遍 → 尝试改一个小地方（比如把推送目标从Slack改成飞书）。

**我从0搭第一个Agent用了50分钟。从模板改一个用了15分钟。** 这就是差别。

### 第4步：设定一个"3天期限"

告诉自己：3天内如果搭不出来一个能用的Agent，就用扣子。不是每个工具都适合每个人。如果你在Dify上花了3天还是觉得"这个平台不是给我设计的"——**这不是你的问题，这是产品定位的问题。** 用扣子，效果一样，方式更简单。

## 最后一个反思：为什么我愿意花30天学Dify

坦白说，如果我只是需要"让AI帮我干点活"，扣子完全够用。甚至更好用。

但我选择花30天学Dify，是因为一个念头：**我不只想"用AI"——我想"掌握AI"。**

扣子让我跑得更快。Dify让我知道引擎盖下面在发生什么。

**当你第一次看到自己搭的工作流跑通——AI搜索了信息、处理了数据、推送了结果——那种感觉和你"点一个按钮就生成的"完全不同。你知道每一步在做什么。你能修任何坏了的地方。你能随时加新的能力。**

这就是Dify的不可替代之处：**它不只是一个工具——它是一个让你理解"AI能如何被编排"的学习平台。**
